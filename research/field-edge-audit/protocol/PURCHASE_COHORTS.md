# Target-label purchasing cohorts

The camera receives a calibration window from the deployment's own site. Subsequent evaluation frames are disjoint. All policies, including their frozen, forced-update and published-review score controls, use the same candidate identities, budgets and possible test arrivals for a given site, seed and run. A frame's true calibration label becomes available only after a chargeable remote transaction in the purchasing protocol. Test labels belong to a separate scoring step.

| Site | Eligible calibration photographs | Evaluation photographs | Split and time |
| --- | ---: | ---: | --- |
| Cornell | 450 | 1,353 | Published fixed bank and holdout from this study, retaining one representative per perceptual component. Five label-independent hash replay orders. |
| Kashmir | 256 | 384 | New calibration bank from the same 5,612-image release. The original 128-per-source-class evaluation pool is kept intact. Five hash orders. |
| Latvia | 590 | 579 | One representative per component on the earliest five capture dates. All images from the nine later dates remain in evaluation, in original EXIF order. |

Cornell and Latvia candidates come from the already fixed splits in the original repository. For Kashmir, the parquet's SHA-256 must match the pinned archive in `data/kashmir_source.json`. The builder excludes the original 384 test IDs and sorts candidates by a salted SHA-256 of the source-image bytes. It rejects exact hashes and 64-bit perceptual-hash distances of five or less against the original test panel, Cornell, Latvia, the prior upstream fingerprints and all previously retained candidates. It accepts the first 256 remaining candidates. Only after these identities have been fixed does the builder join the reference labels. This selection gives each candidate image equal eligibility independent of its reference class. The preexisting Kashmir benchmark was sampled evenly over the three source classes. The provider supplies processed, sometimes augmented images without recoverable parent-leaf IDs; passing the hash screen does not prove independence of plant individuals.

The evaluator derives the same 20 nested panels of 128 candidate positions for all three camera variants by hashing an opaque identifier with the draw seed. Within-site calibration/evaluation content hashes are disjoint. The bank and the evaluation identities do not change across runs. The default test stream uses the first of the five label-independent orders for Cornell/Kashmir and the unique chronological order for Latvia. Late Latvia images can include repeated leaf views. Use capture dates when resampling that evaluation. All local training takes place within the site's designated calibration window. This design measures a decision before the evaluation window and leaves production continuous retraining untested.

The two edge architectures are the released AgriTinyVision 160-pixel MobileNetV2 and the independently sourced MobileNetV4-Conv-Small with its fixed PlantDoc head. An additional V2 numerical sensitivity uses the original ESP-PPQ scales in host simulation. Every variant uses the same 224-pixel quality-75 JPEG, byte length and PlantDoc-balanced DINO expert. For four original Kashmir benchmark images, the pipeline cross-checks all three edge feature extractors, numerical-grid probabilities, the DINO representation and JPEG payload hashes against saved references before accepting the new bank. The feature simulation is distinct from measurement on the physical board.

Run from the licensed workspace after preparing the earlier feature archives, the MobileNetV4 caches and the `esp-grid-cache` as described in the corresponding protocols. Put the AgriTinyVision v0.1.0 release's `tinyvision.json` under `data/raw/esp-ppq/`. Run `python scripts/purchase_cohorts.py` and `python scripts/purchase_cohorts.py --verify-only`. Private contents, including the new visual representations, are written exclusively below `data/raw/purchase_cohorts/`. The distributable cohort audit contains only counts, dates, minimum distances and aggregate identity fingerprints. The read helper `load(site, backbone)` accepts sites `cornell`, `kashmir`, `latvia` and variants `v2`, `v4`, `v2grid`. The original two variants expose 1,280-dimensional FP32 activations. The grid exposes signed integer codes with a fixed 1/32 activation scale. Tests and calibrated examples have separate array prefixes; an evaluator should pass only the allowed prefix to a purchase policy.
